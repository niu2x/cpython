# 第一题：给 list 增加 `extend` 和 `pop` 方法

在 `test/1d5735e8462` 分支完成。共同交付要求和评审标准见 [README](README.md)。本题现在可以开始。

## 目标

当前 `list` 对象（`Objects/listobject.c`）只有
`append / count / index / insert / sort / remove / reverse`。新增两个方法：

- `l.extend(seq)` —— 把序列 `seq` 的每个元素依次追加到 `l` 末尾。
- `l.pop([index])` —— 删除并返回下标 `index` 处的元素；不带参数时操作最后一个元素。

训练重点：类型对象的方法表与属性查找、参数解析、序列协议、引用计数与错误路径。

## 语义规定

- `extend` 接受任意序列（按序列协议逐个取元素）。参数不是序列时抛 `TypeError`，
  并且此时 `l` 保持不变。
- `extend` 在取元素过程中若某个元素取值抛异常，异常原样传播；允许 `l` 已被部分追加，
  但不得泄漏引用、不得崩溃、不得破坏 `l` 自身的一致性。
- `l.extend(l)`（自我扩展）必须有明确、可测试的行为，不能死循环或越界。
- `pop()`：空列表抛 `IndexError`。
- `pop(i)`：`i` 为负数时从末尾计数；越界抛 `IndexError`。
- 参数个数错误、参数类型错误抛 `TypeError`。
- 方法的返回值是 `None`（`extend`）或被删除的元素（`pop`），引用所有权正确转移。

## 实现约束

- 只修改 `Objects/listobject.c`（必要时改 `Include/listobject.h`）。不新增文件、不改
  opcode、不引入新的全局状态。
- 复用现有内部结构（`listobject`、`list_methods[]`、`list_getattr` 及已有静态辅助函数），
  不要绕过序列协议另起一套取元素逻辑。
- 不得改变现有方法的可见行为。

## 验收要求

1. `extend` 对 tuple、list、string 都按序列协议正确工作。
2. `extend` 对非序列抛 `TypeError` 且列表不变。
3. `pop()` / `pop(i)` / 负数 / 越界 / 空列表的返回与异常完全符合上面规定。
4. 引用计数正确：反复 `pop`、对列表元素执行 `del` 后列表仍可用，无泄漏、无悬空引用。
5. 自我扩展有确定行为。

## 测试要求

必须覆盖：

| 情况 | 要求 |
| --- | --- |
| `extend` 各类序列 | 逐一验证结果 |
| `extend` 非序列 | 抛 `TypeError` 且列表不变 |
| `extend` 取元素中途报错 | 原异常传播，进程不崩溃 |
| `l.extend(l)` | 行为确定且不越界 |
| `pop` 空/越界/负数/默认 | 返回值或 `IndexError` |
| 参数个数与类型错误 | `TypeError` |
| 引用计数 | 反复增删后对象仍可用，可用 `id()`/生命周期观察 |

测试必须有自动判定与非零失败退出状态，不能只检查打印输出“看起来正确”。

## 设计说明与评审追问

提交时必须：

1. 给出 `extend` 的实现思路：逐个取元素直接追加，还是先复制到临时 list 再拼接，各自
   的失败语义与代价。
2. 说明 `l.extend(l)` 为什么不能“边遍历边追加”。
3. 说明 `pop` 返回元素时，引用如何从列表内部转移到调用者。
4. 说明越界与空列表为何用 `IndexError` 而不是 `ValueError`，并与现存方法保持一致。

评审追问：

1. 序列协议取元素用的是哪个协议槽？取不到时如何抛异常？
2. 你在 `extend` 失败路径上如何保证不泄漏已经 `INCREF` 的引用？
3. `list_methods[]` 与 `list_getattr` 的约定是什么，新增方法为何只需改这两处？
